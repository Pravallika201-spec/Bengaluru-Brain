## Known data-freshness gap

No TomTom API key is configured in this environment (`TOMTOM_API_KEY` unset), so the collector cannot run and `feed_status` correctly reports `NO_LIVE_FEED`. The collector itself (`traffic_module/data/collect_live_traffic_history.py`) was audited this pass and confirmed production-ready — it validates responses, timestamps observations, and appends to the historical dataset — it simply has nothing to fetch without a real key. Everything downstream honestly reflects this — no traffic response in this system claims a live feed exists when it does not.

## Ward identity — RESOLVED this pass

**Previously**: `traffic_module/backend/ward_stress.py` used its own simulated ward numbering (integer IDs 1–369, arbitrary, with real duplicate collisions — Silk Board and HSR Layout both `ward: 174` by coincidence) that was unrelated to `integration/geo/ward_registry.json`'s real OSM ward IDs.

**Now**: a single canonical identity model. `location_data.py` computes each named location's real `canonical_ward_id` via point-in-polygon against the real ward boundaries; `ward_stress.py` iterates the real 369-ward registry directly instead of `range(1, 370)`. The old arbitrary numbers are preserved as `legacy_ward_id` for backward-compatibility documentation only — never used in any live computation. Verified: 0 ID mismatches across `/api/locations`, `/api/ward-stress`, and `/api/wards/full/schema` (see TEST_REPORT.md §Priority 2).
